# Протокол замеров: чанкинг и качество поиска (практика 2)

## Исходные данные

Три файла формата Markdown, суммарно ~4.0 МБ. Страниц у Markdown нет,
поэтому метаданное `page` у всех чанков равно 0. Именно эти имена
попадают в поле `source` и в `expected_sources` проверочного набора.

| Файл | Размер | Структура |
| --- | --- | --- |
| `tk_rf.md` | 1 702 283 байт | Трудовой кодекс РФ: 540 статей (`#### Статья N`), 14 разделов |
| `rost_guide.md` | 2 252 625 байт | Руководство кадровика: 279 разделов (`##`), 25 подразделов (`####`) |
| `post_858.md` | 58 546 байт | Постановление № 858 с типовой формой трудового договора: 12 разделов (`##`) |

Очистка (`clean_text`) убрала 814 строк-сносок редакций `(в ред. …)` и
`(введен …)` из `tk_rf.md`, строки-разделители `----` из `rost_guide.md`,
разрывы слов по переносу и цепочки пробелов. Переводы строк сохраняются,
чтобы заголовки статей оставались различимыми внутри чанка.

## Словарь рубрик

Правило: ключевые подстроки в нижнем регистре, поиск по тексту чанка,
проверяется по порядку, возвращается первая совпавшая рубрика.

| Рубрика | По какому правилу присваивается |
| --- | --- |
| `termination` | Есть «увольн», «прекращ» или «расторж» |
| `payment` | Есть «заработн», «оплат», «преми» или «удержан» |
| `working_time` | Есть «рабочее время», «рабочего времени», «отпуск», «испытан» или «смен» |
| `mandatory_terms` | Есть «трудовой договор», «трудового договора» или «обязательн» |
| `general` | Рубрика по умолчанию: ни одно правило выше не сработало. В ТЗ её нет — это резервная рубрика, чтобы не оставлять чанки без категории |

`contract_check` из ТЗ не присваивается чанкам: это тип пользовательского
запроса («проверь мой договор»), а не рубрика документов базы знаний.

Распределение при выбранных параметрах (2 369 чанков): `general` 785,
`termination` 568, `payment` 374, `working_time` 357, `mandatory_terms` 285.
Пустых категорий нет, у каждого чанка заполнены `source`, `page` и
`category`; поиск с фильтром `where={"category": "payment"}` возвращает
только чанки категории `payment`.

## Замеры

Оба прогона: `python ingest.py` (переиндексация с нуля + `evaluate_retrieval`),
корпус один и тот же, менялись только параметры нарезки в `config.py`.

| № | CHUNK_SIZE | CHUNK_OVERLAP | Чанков в индексе | hit-rate@5 | hit-rate@1 |
| - | ---------- | ------------- | ---------------- | ---------- | ---------- |
| 1 | 512 | 64 | 4763 | 80% (4 из 5) | 60% (3 из 5) |
| 2 | 1000 | 100 | 2369 | 100% (5 из 5) | 20% (1 из 5) |

`hit-rate@1` измерен в обоих прогонах и приведён как вторичная цифра:
`hit-rate@5` варианты различает (80% против 100%), так что выбор по нему
не нужен. Замер: `from ingest import evaluate_retrieval; evaluate_retrieval(k=1)`.

**Выбранные значения и основание.**

Приняты `CHUNK_SIZE = 1000`, `CHUNK_OVERLAP = 100`: единственный вариант
с hit-rate@5 = 100% (5 из 5) против 80% у 512/64. Победитель записан
в `config.py`. По вторичному числу (hit-rate@1) выигрывал 512/64 — 60%
против 20%, — но primary-метрикой объявлена hit-rate@5, и именно по ней
сделан выбор. Отмечу: больший чанк чаще удерживает ответ целиком,
зато хуже ранжирует первый результат — это видно по колонке hit-rate@1.

## Уточнение метрики из технического задания

ТЗ (Практика 1) объявило `hit-rate@5 ≥ 0.80` — 4 из 5 вопросов при шаге
шкалы 20%. При первом замере (512/64) получилось ровно 80% (4 из 5),
вопрос об увольнении в период испытания вернул `rost_guide.md` вместо
ожидаемого `tk_rf.md`. При втором замере (1000/100) — 100% (5 из 5).
Число уточнять не требуется: порог 0.80 выполнен, оставлен как цель.
